# 世界演变系统设计计划 v0.1

> 状态：A0.0.5 数据恢复与管理面板里程碑已实现，进入 SillyTavern 实测阶段
> 日期：2026-09-25
> 目标：先在 SillyTavern 中跑通一个可验证的最小闭环，再逐步扩展为独立的世界演变系统。

## 1. 项目定位

“世界演变”是一个独立的后台模拟模块，主要负责：

- NPC 自主行动；
- 组织与阵营的变化；
- 社会关系和社会事件的变化；
- 地点与环境的变化；
- 待发生事件、计划和因果链的推进；
- 将适合主 AI 读取的结果同步为世界书条目。

它不是另一套 MVU，也不替代现有数据库。

### 1.1 三套数据的职责边界

```text
原生 MVU
  文游卡自己的即时变量，例如数值、装备、任务和卡片专用状态

shujuku
  主角已知的结构化资料，例如角色档案、联系方式、物品和纪要

世界演变
  主角视线之外仍在发生的后台行动、计划、社会变化和未来事件
```

世界演变不再维护 `addon_data`，不输出 `<AddonJSONPatch>`，也不把自己的后台状态写回原生 MVU。

## 2. 插件定位与触发时序

世界演变是独立、可选的增强插件，不是主游戏流程必需的工作流阶段。

- 插件关闭时，主 AI、原生 MVU 和 shujuku 按原流程运行，不受影响；
- 插件启用时，才监听前置流程完成信号；
- 插件只在原生 MVU 已完成、shujuku 已完成或明确跳过后开始一次演变；
- “最后触发”描述的是插件在一轮游戏中的接入时机，不代表它被并入主工作流。

启用插件时的默认接入顺序：

```text
主 AI 回复
  ↓
原生 MVU 完成解析与更新
  ↓
shujuku 数据库更新完成，或明确判定为本轮跳过
  ↓
世界演变插件接收完成信号
  ↓
筛选本轮需要行动的对象
  ↓
一次性批量生成后台变化
  ↓
校验并原子提交世界演变数据
  ↓
同步受影响的 WorldEvolution-* 世界书条目
  ↓
下一轮主 AI
```

如果 MVU 或数据库阶段失败，默认不触发本轮世界演变；如果某个阶段明确跳过，则允许插件继续接收本轮完成信号。

插件本身内部仍有自己的处理流程：

```text
接收触发
  ↓
读取输入快照
  ↓
筛选候选对象
  ↓
批量生成后台变化
  ↓
校验并提交独立数据
  ↓
同步 WorldEvolution-* 世界书条目
```

这些是插件内部步骤，不应被理解为主游戏工作流新增了多个阶段。

## 3. 第一版必须验证的最小闭环

第一版不追求完整数据库和完整 UI，只验证 SillyTavern 内的真实运行链路：

```text
Git import 脚本加载
  ↓
等待/接收 MVU 完成信号
  ↓
读取本轮消息、MVU 快照和可用上下文
  ↓
选出最多 N 个候选 NPC
  ↓
调用一次世界演变 AI
  ↓
批量更新至少两个 NPC
  ↓
写入独立世界演变存储
  ↓
创建或更新一个 WorldEvolution-* 世界书条目
  ↓
在调试面板显示完整结果
```

### 3.1 第一版的成功标准

- 能通过远程 Git `import` 在 SillyTavern 中加载；
- 不依赖 `addon-mvu`；
- 能在 MVU 完成后触发，而不是在主 AI 输出中途触发；
- 不修改 shujuku 表格；
- 能批量处理多个 NPC；
- 同一楼层重跑不会重复追加同一事件；
- 刷新页面后仍能读到世界演变数据；
- 能创建、更新并删除自己管理的世界书条目；
- 能在失败时保留错误信息，不提交半成品；
- 能通过调试面板观察输入、候选对象、AI 输出和提交结果。

## 4. 输入、筛选和批量处理

### 4.1 世界演变输入适配层

世界演变核心不直接绑定某一种 MVU 字段结构。先建立统一输入：

```ts
type WorldEvolutionInput = {
  chatId: string;
  messageId: number;
  latestMessage: string;
  currentTime?: string;
  currentLocation?: string;
  mvuSnapshot?: unknown;
  mvuChangeSummary?: unknown;
  databaseSummary?: unknown;
  activeCharacters: string[];
  recentWorldEvents: string[];
};
```

MVU、工作流助手和 shujuku 只负责提供适配后的输入；世界演变核心只消费统一结构。

### 4.2 候选对象来源

候选对象由以下来源合并去重：

- MVU 本轮变化明确关联的角色或组织；
- 当前场景中出现或被提及的角色；
- 有到期计划或待办行动的 NPC；
- 受近期事件影响的组织、地点或角色；
- 当前时间、地点变化后需要重新评估的对象；
- 用户手动指定的对象。

### 4.3 数量控制

“最多处理对象”不是写死在提示词中的常数，而是用户设置：

```text
本轮最多处理 NPC：N
本轮最多处理组织：N
本轮最多处理地点：N
本轮最多生成新事件：N
```

筛选器先按优先级排序，再截取上限。优先级至少包括：

1. MVU 直接关联；
2. 当前地点/当前场景关联；
3. 待办计划到期；
4. 最近事件影响；
5. 用户手动指定。

## 5. 世界演变数据模型（雏形）

第一版只实现能支撑最小闭环的集合，字段保持可扩展：

```text
worlds
  世界与聊天的归属、当前 revision、暂停状态

entities
  NPC、组织、地点、社会节点等实体的稳定身份

entity_states
  实体当前状态、目标、地点、可见性和更新时间

events
  后台行动、事件结果、影响对象、发生时间和来源楼层

scheduled_events
  未来计划、触发条件、预计时间和完成状态

checkpoints
  可恢复的版本快照

revisions
  每次批量提交的变更摘要和审计信息
```

### 5.1 可见性

每条状态或事件必须有可见性等级，避免后台信息无条件泄露：

```text
backstage
  仅世界演变内部使用

ai_context
  可以提供给主 AI，但不代表主角已知

protagonist_known
  主角已经知道

revealed
  已经在剧情中公开揭示
```

### 5.2 稳定身份

显示名可以是中文全名，但内部必须有稳定 ID：

```text
entityId: npc_01
displayName: 角色甲
```

角色改名时迁移显示名和关键词，不改变历史事件归属。

## 6. AI 输出协议

世界演变 AI 不直接执行 SQL，不直接操作 IndexedDB，也不直接修改世界书。

第一版采用单一结构化块：

```xml
<WorldEvolution>
{
  "baseRevision": 18,
  "updates": [
    {
      "type": "npc",
      "id": "npc_01",
      "changes": {
        "current_location": "北境城",
        "current_goal": "调查失踪商队"
      }
    }
  ],
  "events": [
    {
      "eventId": "EV-0001",
      "type": "npc_action",
      "actors": ["npc_01"],
      "summary": "角色甲开始调查失踪商队",
      "visibility": "ai_context"
    }
  ],
  "scheduledEvents": []
}
</WorldEvolution>
```

### 6.1 提交前校验

- JSON 必须可解析；
- `baseRevision` 必须匹配当前版本；
- 实体必须存在，或明确标记为新建；
- 字段必须属于允许更新集合；
- 不允许修改聊天归属和内部 ID；
- 事件 ID 不得重复；
- 不允许越过可见性规则；
- 不允许把后台秘密自动写成主角已知；
- 批量数量不能超过用户设置；
- 所有更新通过后才一次性提交。

任何一项失败，整批不提交，只记录失败原因。

## 7. 世界书同步设计

世界演变可以与 shujuku 使用同一个世界书，但使用独立命名空间和明确前缀：

```text
WorldEvolution-NPC-角色甲
WorldEvolution-NPC-角色乙
WorldEvolution-组织-某某组织
WorldEvolution-地点-北境城
WorldEvolution-事件-EV-0001
WorldEvolution-全局
```

### 7.1 两种注入模式

```text
constant
  常驻世界演变索引、当前后台时间、近期动态摘要、待发生事件摘要

keyword
  按 NPC 姓名、组织名、地点名、事件 ID 触发的详细条目
```

常驻条目只保存短索引，不放所有 NPC 的完整状态。详细状态放在关键词条目中。

### 7.2 条目内容边界

每个条目明确标注来源：

```text
<世界演变后台状态>
...
</世界演变后台状态>
```

世界演变条目不重复复制 shujuku 的角色档案。两者同名时：

```text
shujuku
  公开资料、主角已知经历、联系方式、物品和纪要

WorldEvolution
  当前后台位置、真实目标、秘密行动、组织内部变化和未公开事件
```

### 7.3 同步策略

- 只更新本轮受影响的条目；
- 删除条目前先确认实体或事件已永久失效；
- 世界书同步失败不回滚已提交的数据库事件，但标记为待同步；
- 下一轮启动时重试待同步条目；
- 支持“只重建世界演变条目”，不重建 shujuku 条目。

## 8. 存储和分支策略

第一版优先使用浏览器 IndexedDB，原因是：

- 与 shujuku 存储隔离；
- 可保存事件日志和版本；
- 支持按聊天/世界分区；
- 可导入导出 JSON；
- 后续可实现 checkpoint 和回滚。

第一版至少需要：

- 按聊天或世界隔离；
- 当前版本号；
- 事件追加记录；
- 当前状态投影；
- JSON 导出/导入；
- 同楼层幂等键；
- 基础 checkpoint。

暂不实现跨设备同步、远程服务器和复杂多分支合并。

## 10. 发布方式

### 10.1 第一阶段：Git import 原型

继续支持类似：

```ts
import 'https://testingcf.jsdelivr.net/gh/用户名/仓库名@版本/dist/world-evolution/index.js';
```

原型阶段优先使用当前项目的脚本构建方式，快速迭代输入协议、触发时机和调试面板。

### 10.2 第二阶段：SillyTavern UI Extension

当以下内容稳定后，再包装为正式 UI Extension：

- 数据模型；
- 触发时序；
- AI 输出协议；
- 世界书同步；
- 存储和回滚；
- 基础设置；
- 版本迁移。

两种入口共用同一份核心代码：

```text
核心模块
  ├─ Git import 入口
  └─ SillyTavern UI Extension 入口
```

不建议第一版直接做服务器插件。当前需求在浏览器端即可验证，服务器权限和部署复杂度留到以后。

## 11. 开发阶段与里程碑

### M0：设计冻结

- 确认输入适配器；
- 确认世界演变输出协议；
- 确认世界书命名；
- 确认批量对象上限；
- 确认失败时不提交；
- 确认本轮重跑幂等规则。

### M1：SillyTavern 加载探针

- Git import 可加载；
- 显示脚本版本和状态；
- 能卸载；
- 能记录当前聊天和楼层；
- 不写 MVU、不写 shujuku、不改世界书。

### M2：MVU 完成触发探针

- 能等待或接收 MVU 完成；
- 能记录本轮 MVU 前后快照或变化摘要；
- 能区分新楼层、同楼层重跑和手动触发；

- 跨设备同步；

- 一开始就制作完整复杂 UI。

## 13. 验收场景

至少准备以下测试：

1. MVU 完成后触发一次，新增两个 NPC 后台行动。
2. 本轮没有数据库变化，但 MVU 已完成，世界演变仍可按规则运行。
3. MVU 未完成时，世界演变不运行。
4. 同一楼层重跑，事件不重复。
5. AI 输出非法 JSON，数据库不发生部分写入。
6. 批量候选超过上限，只处理用户设置数量。
7. 世界书同步失败，数据库事件仍保留并进入待同步队列。
8. 刷新页面后，事件、revision 和调试记录仍可读取。
9. 同名角色同时存在 shujuku 条目和 WorldEvolution 条目时，内容边界清晰。
10. 手动暂停某 NPC 后，该 NPC 不被自动选入候选。

## 14. 当前结论与原型实现状态

世界演变不是主游戏流程的必需阶段，而是一个可以随时启用或停用的独立增强插件。

已经按“一次性先做可运行原型”的方向实现 Git import 版，覆盖完成事件接入、MVU 快照读取、批量候选筛选、AI JSON 校验、IndexedDB 独立存储、世界书同步和基础调试面板。它尚未等于通过真实 SillyTavern 环境验收：需要导入运行，确认工作流完成事件能抵达、AI 提供方接受结构化输出，并验证配置的世界书名称存在且条目符合预期。

当前实现边界：

- 插件本体默认关闭；启用后可选择自动运行或从面板手动运行；
- 自动运行要求工作流助手完成事件报告至少一个任务成功，且本轮未取消；
- 启动时优先考虑本轮 ReplicaEnum / 手动候选 / 待处理事件对象，其余已有对象按最久未更新轮转；
- 数据只存浏览器 IndexedDB，按聊天隔离；清除浏览器站点数据前应先从面板导出备份；
- 同一聊天楼层一旦成功处理，重复触发会跳过，避免重复追加事件；当前尚无“撤销某次演变并重跑同楼层”的事务性回滚；
- AI 结构化输出错误或 IndexedDB 不可用时不写入；世界书同步失败时已保存的世界演变数据不会回滚，后续运行会再次尝试同步；
- 当前 UI 已提供对象库、事件/计划、运行记录、checkpoint、最近 checkpoint 回滚和世界书同步重试；完整 revision 差异视图仍可作为后续增强。

A0.0.2 新增的运行时保护：

- 楼层进入单并发队列，同聊天/同楼层去重，并支持失败自动重试；
- 自动触发会等待楼层文本连续稳定；工作流助手存在时以本楼运行快照的成功/失败为准；
- 每次排队、执行、成功、跳过和失败都会写入 IndexedDB 运行记录；
- 楼层正文指纹参与幂等判断；同楼层重新生成时，若上一轮世界演变正是该楼层，先回滚上一轮投影再生成新结果；
- AI 调用器可注入模拟实现，测试不需要调用真实 API；
- 世界书同步失败不会回滚已提交的世界状态，而会保留错误记录，后续运行可重新同步；
- 面板显示最近楼层运行记录，并可调整重试、稳定等待和对象数量设置。
- 面板增加对象库搜索/类型筛选、事件与待办查看、失败楼层重试，以及对象状态的手动编辑/删除。
- IndexedDB 备份兼容旧版本数据；启动或切换聊天时会把中断的 queued/running 记录标为可重试失败，并重试待同步世界书。
- 当前楼层前置上下文同时包含 MVU 快照、工作流结果摘要和 `AutoCardUpdaterAPI` 可提供的数据库表快照。
- 每次成功演变自动保存 checkpoint；面板可手动创建和回滚 checkpoint。

下一步应先由用户在 SillyTavern 完成实测，再根据日志迭代；之后再决定是否进入对象编辑、版本回滚和正式 UI Extension。

第一版真正需要冻结的只有四件事：

```text
1. 什么时候触发；
2. 给世界演变 AI 什么输入；
3. AI 返回什么结构；
4. 返回后保存到哪里。
```

只要这四件事跑通，后续的组织、社会、环境、事件链、回滚和正式插件界面都可以在同一套独立核心上逐步增加。
