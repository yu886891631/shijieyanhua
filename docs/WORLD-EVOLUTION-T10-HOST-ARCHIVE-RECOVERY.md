## 1. 本阶段交付与真实边界

已实现独立命名空间、可信宿主网关契约、模拟持久宿主、T4/T9 接线、稳定消息/回复页身份、整轮保存确认、有效祖先恢复、复制/分支及只读恢复面板。它们使用同一套模板、数据、固定 SQL、完整快照和提交协议，不引入另一套“宿主版数据库”。

这里的“宿主适配完成”指协议、网关及模拟宿主的实现与故障验证，不表示当前酒馆已经具备所要求的持久写入保证。当前仅有的 TavernHelper 观察入口明确为
`memory-only`、`writable: false`。不会把 `getVariables` / `getChatMessages` 紧接写入后的内存结果称为可靠存档。

真实 `saveChat`
的落盘边界、独立读回以及保护所有相关写入者的原子检查仍未验证；未新增服务器 CAS 接口，也未将某个普通 Promise 或模块内锁冒充此能力。没有这些保证时禁止正式写入，不降级回旧 IDB。真实聊天刷新、删楼和分支验收仍需指定测试聊天与授权，属于明确待验收项。

## 2. 权威存档、命名空间与无损合并

- 聊天变量根中的 `world_evolution_sql_t10`：保存世界/聊天/分支身份、宿主绑定、T4 存档、提交依赖回执和安全请求记录。
- 每页 `swipes_data.world_evolution_sql_t10`：仅保存稳定 `messageId` / `swipeId`。
- 其余聊天变量、正文、姓名、隐藏状态、所有回复文本、MVU 数据、TavernDB 数据及 `swipes_info` 不改写。
- SQLite / IDB / 展示缓存不再被接入为另一份权威；没有缓存仍可从 JSON 恢复，错误缓存被丢弃。
- 首次初始化和新增身份登记是显式动作；无助手楼层不能落盘首次状态，不造消息或伪造锚点。旧库默认不读写、不自动迁移，T13 负责迁移。

T4 协议新增 `t10-host` 模式及 `chat-*` 稳定 ID，同时保留原 `t4-sandbox` /
`sandbox-*`。模式与身份必须对应，网关模式必须一致。现有 T4–T9 沙盒流程保持兼容。

## 3. 保存边界与跨实例互斥

宿主驱动必须由可信集成代码提供，而不是从用户 JSON、面板开关或导入数据取得权限：

1. 明确环境、目标版本、验证依据及支持范围。
2. 独立读取持久 JSON，不能用当前页面对象代替。
3. 对完整文档执行原子版本比较和写入，覆盖其他插件同时写入的冲突；仅检查本插件 revision 不够。
4. 实际写入点检查当前角色/聊天绑定、原文档指纹、取消信号及同步授权。
5. 只有能确定零写入的失败才报告 `SAVE_FAILED`；回执丢失、未知运输错误和读回失败视作待确认。

网关先基于最新持久文档合并自己的字段，然后携带该完整文档的指纹到 CAS。等待期间任何正文、回复页或其他插件字段变化，都拒绝这份旧合并，不覆盖新值。两个独立网关实例共用模拟宿主时，只有一份并发提交能成功。授权撤销/过期的迟到写入也被拒绝。

完成写入后，T4 单独读回完整提交，确认同一 `runId` / `commitId`
/ 范围 / 指纹后才切换正式内存视图。保存未知时仅查询对账，不重跑 SQL 或 AI；已确认同一不可变提交重复保存零新增版本。取消不能撤回已经到达原子写入点的存档，最终以读回事实为准。

模拟宿主的同步 JSON 赋值只证明 fixture 中的这些行为，绝不证明真实酒馆服务器也有 CAS。当前 `verified-host`
契约只声明单服务器聊天范围；不承诺多设备协同或分支合并。

## 4. 真实楼层形态与确定性恢复

宿主文档采用 TavernHelper `include_swipes: true`
的字段形态，数字楼层/回复页索引仅用于当次定位，不作为持久身份。稳定身份由显式登记产生；新增楼层/回复页不会给旧记录重新编号。登记冲突或身份缺失明确阻断。

每次提交绑定当前助手页及此前消息前缀的有序依赖，包含稳定身份与正文/角色/姓名/隐藏状态指纹。这是保守依赖范围；首版不声称精确识别自然语言中每一条最小因果边。未读取的新后续楼层和未选中的新增回复页不使旧前缀失效；插楼、改楼、删楼、改变被选回复或顺序则重新检查相应依赖。

恢复时：

1. 验证聊天绑定、模板、初始快照和继承依赖。
2. 按提交顺序检查父链、版本、固定日志、完整快照、提交和依赖回执指纹。
3. 使用最后一个有效完整快照；从第一项依赖失效/损坏开始，后续提交全部列入待处理尾部。
4. 恢复该有效账本里的世界时间、表频率和轮转位置，不使用当前现实时间或新默认模板。
5. 不执行 AI，不自动收费追平，不重复应用快照已经覆盖的 SQL。

前置 T4 的固定日志重放仍是显式工具，可在兼容模板上执行并比对每步指纹；本阶段宿主恢复默认选择完整快照，零 SQLite 执行。损坏的起始模板/继承依赖不由缓存或默认种子替代。

失效尾部保持原始 JSON，不自动删掉或重封签。有效祖先可只读展示，但不能把它伪装成当前可写头。后续显式恢复/分支操作需先确认范围；这类日常历史操作入口由 T11 收口。

## 5. 请求预留、刷新与事件

T9 宏观及微观、所有客户端重试均在假传输开始前调用统一预留钩子。T10 先将无 Key 的记录写入并独立读回，才允许发送：运行身份、拥有者、基准头、锚点/依赖、阶段、已预留次数、冻结上限及指纹。

这不是精确服务商账单：预留后但发送前中断，也保守记作“结果/费用可能未知”。预留失败/回执不明则停止运输。记录不含 URL、headers、API
Key、原始供应商错误或完整请求提示词。

- 两个入口争抢同一触发或另一未完成运行时，持久 CAS / 拥有者 / 未完成记录阻止双发。
- 相同实例仍有效的显式续跑沿用 T9 私有暂存、冻结配置和累计额度。
- 跨刷新不恢复未保存暂存，不自动重发；已存提交可确定恢复，未完成记录保持待处理。
- 未完成记录可显式放弃，保留发送次数与记录，不自动清空证据。依赖已经失效时不绕过其检查去写放弃结果。
- 刷新、聊天切换、复制/分支、删楼、编辑/更新、swipe/回复删除、重生成、取消等驱动事件会作废会话并取消整轮；事件订阅可卸载。
- 实际酒馆事件桥仍未在旧入口注册，避免本轮新增监听器影响当前游戏；驱动订阅契约和模拟事件已覆盖。

## 6. 独立复制与单父分支

复制来的命名空间仍带原聊天绑定，不能直接成为可写世界。显式转换时：独立复制生成新世界/分支/聊天身份；同世界分支保持世界 ID，但采用新 branch/chat
ID。

只继承指定截止点的不可变历史，目标生成新消息/回复页 ID，逐前缀比对内容并建立来源到目标的映射。来源历史自包含于目标材料，不共用可变头/缓存/队列。源聊天后来删楼不会使独立目标失效；目标自己的继承依赖变化则阻断，不能保留已经失去依据的继承事实。

只有验证后的明确目标命名空间允许安装这份提案；已有不同目标世界不被自动覆盖。首版采用有序前缀映射，不支持猜测索引漂移或任意分支合并。
