> 文档版本：2.8（重新打开 U11-D，修复工作台样式隔离与缩放布局回归）
> 日期：2026-10-02
> 当前状态：U11-A/B/C 已完成；U11-D 前两轮记录保留，但后续复核发现 125% 底部裁切和总览窄列问题，现重新打开补修；alpha.15 候选与固定提交的导入包已生成，待推送和用户导入验收

## 1. 目标

对世界演变工作台进行一次整体视觉与交互一致性整理。重点不是新增世界演变能力，而是让每个页面的信息层级、布局、颜色、控件和说明方式看起来属于同一套产品，并让常用操作更容易理解。

采取“先逐页查看和讨论，再综合设计，最后按页面实施验收”的方式：

1. 用户逐页提供实际运行截图；
2. 每页单独记录现状、问题、建议和待确认事项；
3. 所有页面看完后，统一整理跨页面规范和实施顺序；
4. 只有用户明确说开始修改后，才改 UI 代码；
5. 之后逐页验收，避免页面之间视觉标准漂移。

## 2. 范围与保护边界

本计划针对 SillyTavern 中实际加载的世界演变工作台，包括：

- 共用工作台外壳与左侧导航；
- 总览；
- 世界资料；
- 楼层记录；
- 世界书投影；
- API 配置；
- 自动演变；
- 填表提示词；
- 备份与迁移；
- 外观与显示。

候选范围包括排版、间距、宽度、留白、颜色与对比度、标题层级、空状态、帮助说明、按钮文案、响应式布局和控件易用性。

除非后续单独讨论并得到确认，实施阶段保持以下内容不变：

- 数据库 schema、表格字段、IndexedDB 数据和 revision 事务；
- 世界书投影键、内容指纹、同步与清理逻辑；
- API 配置存储、Key 脱敏、路由优先级和真实调用逻辑；
- 自动演变触发时机、提示词执行逻辑及工作流助手兼容接口；
- 用户现有聊天、楼层、角色卡世界书和 API 配置。

## 3. 全局统一方向（候选，待看完页面后定稿）

### 3.1 页面骨架

- 所有页面沿用统一的左侧导航、面包屑、页面标题、内容区和关闭按钮。
- 统一内容区最大宽度、左右内边距、卡片间距和标题基线，避免有的页面挤在右侧、有的内容铺满、有的页面留白过多。
- 宽屏优先使用稳定的栅格；窄窗口和缩放时自然折行或单列，不产生横向溢出。
- 空状态、加载状态、成功、警告、失败和未配置状态使用一致的文案语气与视觉语义。

### 3.2 颜色与可读性

- 统一浅色、深色等主题中的文字对比度；避免浅蓝字放在浅色背景上难以阅读。
- 区分主要操作、普通操作、危险操作和纯导航入口。
- 选中分类、未选分类和悬停状态采用同一套层级，不让某个页面的深色分类条明显脱离整体风格。
- 状态颜色需与真实状态对应；“尚未运行”不应看起来像“运行成功”。

### 3.3 内容与控件

- 技术术语首次出现时提供简明解释；面向用户的主要标签优先用清晰中文，必要时保留 revision 等内部字段名作为次要信息。
- 卡片标题、说明、计数、表格和操作按钮保持一致的字体层级与对齐。
- 对会修改或删除数据的操作，明确说明作用范围、结果及是否可撤销；不因视觉整理改变原有确认保护。
- 不为填满空间而增加无实际价值的装饰或指标。

### 4.1 共用工作台外壳

**状态：已看图（通过多个页面截图观察），待统一复核。**

覆盖左侧品牌区、聊天标识、导航分组、底部运行状态、版本号、顶部面包屑/标题、revision 标识、关闭按钮和主内容滚动区。

初步观察与建议：

- 多张截图中整体外壳稳定，但聊天标识被截断；可保留省略显示，同时确保悬停或辅助信息能查看完整值。
- 侧栏显示“尚无运行记录”时配绿色圆点，可能让用户误读为健康/成功状态；应讨论中性状态的视觉表现。
- 顶部 `revision 0` 对普通用户偏技术化；考虑改成易理解的“数据版本”或降低视觉权重，但保留需要时查看 revision 的能力。
- 页面导航、页头和内容卡片的左右边缘应建立统一对齐基准。
- 版本信息需避免重复或相互矛盾；发现 API 页面仍显示 `ALPHA.12`，而侧栏为
  `A0.1.0-alpha.13`，该标记应统一使用版本常量或与用户可见版本保持一致。

待讨论：

- revision 是否仍需常驻在顶栏，还是只在世界资料/楼层记录等数据页显示？
- 聊天标识是否需要更明显地表达“当前数据库作用于这个聊天”？

### 4.2 总览

**状态：已看图。**

页面职责：概览当前聊天的世界资料、近期演变、世界书投影状态，并提供常用入口。

截图中可见：欢迎区、NPC/组织与地点/楼层处理/世界书投影四张统计卡、最近楼层、常用入口。

初步观察与建议：

- 页面框架清楚，但主要内容集中于上半屏，下半部留白较大；讨论是否调整内容区密度或卡片布局，不为填空白硬加装饰。
- 最近楼层暂无记录时，空状态显得偏小且靠右；可考虑更明确地解释何时会出现记录，并让空状态在卡片内居中、易读。
- 首页缺少一眼可见的“运行准备状态”，例如自动演变开关、API 路由是否就绪、世界书投影是否可用、最近一次运行结果。只展示简短状态，不展示 API
  Key 或重复配置表单。
- 世界书投影统计值“1”目前缺少计数口径说明；需明确它是托管条目数、投影对象数还是其他指标。
- 常用入口目前包含演变运行、填表提示词、备份与迁移；可讨论是否增加 API 配置入口，或以状态摘要提供跳转。
- “数据库是事实源、世界书是可重建投影”的核心概念值得保留，但欢迎区说明可评估是否更简洁。
- “最近楼层”“常用入口”标题旁的装饰横线显得悬空，可考虑去掉或让分隔线与卡片结构对应。

待讨论：

- 总览是否应该突出“当前是否已就绪”，还是保持纯信息面板？
- 首页默认主按钮是否继续是“打开世界资料”，还是改为当前最需要的下一步操作？

### 4.3 世界资料

**状态：已看图。**

页面职责：按 NPC、组织、地点、社会、环境、事件、计划分类查看和维护当前聊天的世界状态数据。

截图中可见：数据库事实源说明、revision/NPC/事件/楼层记录/检查点统计、当前聊天数据库状态、刷新按钮、七类数据分类、新增记录表单、搜索框和空表。

初步观察与建议：

- 标题、说明、统计数字等浅蓝文字在浅色背景上对比度偏低；需要统一到可读性更好的主题色。
- 五项统计当前呈现为四张一行、第五张单独换行；应重新设计为整齐的单行/均衡网格，并统一 `revision` 等术语的中文展示。
- 七类分类按钮使用较重的深蓝背景，与工作台其他暖色系页面不完全统一；选中态仍需明显，但可调整色彩、尺寸和间距，使其融入公共视觉规范。
- 新增记录主要依赖 JSON 输入；空白初始值 `{"state": {}}`
  对不熟悉数据结构的用户不够友好。讨论是否在保留 JSON 高级编辑能力的同时，提供更直观的字段输入、示例和校验提示。
- “提供给 AI”是可见性选项之一，但单独看截图时容易被误认为普通字段；需要明确它是可见性/上下文范围选项，并解释各选项差别。
- “写入 NPC”等按钮应让新增对象与当前分类的关系清楚；成功、格式错误和字段校验反馈也应统一呈现。
- 数据表的空状态可以保留“当前分类暂无记录”，并将新增入口与该空状态建立更明确的关联。
- 顶部数据库机制说明信息重要但偏技术化，可压缩主句，将 operations 回放、不会重调用 AI 等细节放到帮助说明中。
- 刷新状态和“刷新数据”按钮需明确作用对象是当前聊天数据库；不改变已有数据读取/刷新行为。

待讨论：

- JSON 编辑应作为默认方式、可选高级方式，还是继续保持唯一输入方式？
- “检查点”是否需要改成“恢复检查点”或配简短解释？
- 七类数据分类在窄窗口下采用换行、横向滚动还是下拉分类？

### 4.4 楼层记录

**状态：已看图。**

页面职责：查看每层世界演变运行状态、revision 操作与检查点；必要时创建检查点或按已保存 operations 确定性重建，不重新调用 AI。

截图中可见：数据库机制说明、五项摘要统计、创建检查点/手动重建楼层/刷新记录操作，以及“楼层运行”“Revision 操作”“检查点”三张表。

初步观察与建议：

- 与世界资料页重复出现相同的浅蓝标题/说明、统计数字对比度不足、第五张统计卡单独换行等问题，应优先由全局规范统一解决。
- 当前统计将 revision、NPC、事件、楼层记录、检查点放在一起；对楼层记录页来说 NPC 和事件不直接说明运行情况。建议改为楼层处理数、失败/待处理数、受影响对象数、当前 revision、检查点等与本页职责相关的状态，或精简成更少但更有用的指标。
- 页面上方同时有“创建检查点”“手动重建楼层”“刷新记录”三个操作，层级相近；应突出普通刷新与重要数据操作的区别，并说明手动重建使用已保存 operations、不会重新调用 AI。
- “手动重建楼层”名称可能被理解成重新让 AI 演变该楼层。建议讨论改成更具体的“按楼层重放已保存操作”或在操作旁加说明；无可重放楼层时应禁用或解释不能执行的原因。
- “检查点”用于加速恢复和长历史重建，但属于内部概念；建议提供一句就地解释，避免和普通备份/revision 混淆。
- 三张表的列与用途基本匹配：运行表显示楼层/状态/来源/revision/候选对象/错误，revision 表显示楼层/来源/状态/操作数，检查点表显示 ID/revision/楼层/原因/创建时间。可保留这些审计字段，但降低过长 ID 或技术列的视觉权重，必要时通过详情查看。
- `revision`、`stale`、`operations`
  等中英文混用需要统一：用户可见列名先用中文，技术标识放辅助信息或详情中；状态值也应使用可理解的中文标签。
- 三张表当前都为空，空白内容区域较大。可以分别给出针对性的空状态：尚无运行记录、尚无 revision 操作、尚无检查点，并明确哪些操作会产生相应记录；避免每个表格都只留一大片空白。
- 顶部重复展示数据库事实源与回放说明；可将公共事实源提示收敛成全局帮助信息，在本页重点显示“确定性重建不会调用 AI”和操作范围。

待讨论：

- 用户是否希望查看完整 operations JSON，还是列表先显示摘要、点开后查看详情？
- 手动重建楼层的操作方式、确认步骤和影响范围是否需要在 UI 中进一步解释？
- 当前无运行记录时，是否保留统计卡和三张空表，还是使用更紧凑的引导式空状态？

### 4.5 世界书投影

**状态：已看图。**

页面职责：把数据库中允许投影的世界演变记录同步到当前角色卡的 `primary`
世界书，并检查本插件托管条目的缺失、漂移或孤儿状态。

截图中可见：数据库事实源提示、目标角色卡 primary 世界书名称、托管条目/已同步/待处理失败/缺失漂移孤儿四项统计、立即同步/检查并修复/完整重建操作，以及投影明细表。

初步观察与建议：

- 页面主流程明确，用户能看到目标世界书、投影状态和同步操作；“只写入 WorldEvolution-\* 托管条目，不覆盖用户或 shujuku 内容”的保护说明很重要，应保留并让它更容易读到。
- 与世界资料、楼层记录页相同，浅蓝标题/说明和统计数字在浅色底上的对比度不足；这是跨页面统一问题，不应只在本页打补丁。
- 数据库事实源说明在多个页面重复出现；本页可以缩短为与投影直接相关的说明，详细机制收进统一帮助提示。
- 当前“待处理 / 失败”与“缺失 / 漂移 / 孤儿”把多个不同状态合并显示。建议拆分状态口径或提供点击查看明细，使用户能区分“尚未同步”“同步失败”“数据库应有但世界书缺失”“条目被改写”“已不再需要的孤儿条目”。若空间不够，可保留汇总数字但提供清晰详情列表。
- 三个按钮的风险与效果需要分层说明：立即同步是常规写入；检查并修复可能更新被插件托管的条目；完整重建应明确仅重建当前聊天、本插件拥有的投影条目，不清空整本角色卡世界书，也不触碰用户自建条目或 shujuku 内容。不要仅靠“完整重建”这个名称让用户猜影响范围。
- 目标世界书条目数量只有一条时，统计和表格下方留白很大；可通过更紧凑的状态/目标摘要、表格行高或两栏信息布局平衡，但不为了填满页面而增加无关指标。
- 表格把
  `index`、`synced`、UID、`revision`、内容指纹直接暴露在主要视图中。建议主列表采用可理解字段，例如“投影类型、角色/记录、同步状态、对应版本”；UID 和指纹可放进展开详情或复制按钮，revision 可显示为“数据版本”，状态值翻译成中文。
- 表格中的 `index`
  作为记录 ID/类型重复出现，不像普通用户需要的内容；需要核实它是否只是索引哨兵/清单条目，并决定是否应折叠为“投影索引”或归入技术详情，不应误导成 NPC 等实际世界记录。
- 当前目标世界书名称较长时，应允许折行或通过辅助文本查看完整名称；同时清楚标注它来自当前角色卡 primary 世界书，而非用户可在本页随意切换的数据源。

待讨论：

- “检查并修复”和“完整重建”是否需要分别增加确认/预览，以及各自准确影响哪些条目？
- 普通用户是否需要在主表直接看到 UID/内容指纹，还是只在高级详情中查看？
- 状态统计要采用四张汇总卡，还是改成一条更紧凑的同步状态摘要并提供详细诊断？

### 4.6 API 配置

**状态：已看图。**

页面职责：配置内置 API 预设、主备路由和工作流助手兼容桥接；此处负责编辑，自动演变页不应重复提供 API 编辑表单。

截图中可见：预设列表/创建表单、Endpoint/Key/模型/超时/重试选项、路由选择、内置 API 优先级和工作流助手桥接状态。

初步观察与建议：

- 页面结构已经独立，主要信息和操作都能找到；配置和运行职责分开的方向正确。
- 页面顶部 `BUILT-IN API · ALPHA.12` 与工作台侧栏 `A0.1.0-alpha.13` 不一致；应改为动态版本标识或移除这个重复版本标签。
- 预设表单和路由表单内容集中在卡片右侧，左侧留白过大；需要统一卡片内部布局，让标题、说明、字段、操作按钮形成稳定栅格。
- 预设数量为 0 时的空状态和创建按钮可以更紧密地关联，避免空状态文字像独立的横幅。
- 主路由未选择、备用路由未配置、工作流助手未发现等状态应明显但不制造告警感；用户能一眼知道下一步要做什么。
- API Key 脱敏、本地保存和模拟连接不联网等安全/测试说明需要保持清晰；视觉调整不能暴露 Key 或改变路由行为。
- 自动演变页只显示路由摘要/就绪状态，API 编辑仍只在本页进行。
- 第二组截图中，预设表单字段和操作按钮分散在卡片不同区域：字段聚集右侧、保存/模拟测试按钮落在左下，填写与提交关系不够紧密。建议将预设标题、字段组和对应操作组织成连续表单区；大屏可采用紧凑的两栏结构，而不是把字段推到卡片右侧并留下大片空区。

### 4.7 自动演变

**状态：已看图。**

页面职责：管理世界演变插件启用状态、自动触发、手动运行、候选数量限制、失败重试、稳定楼层读取、世界书同步和当前运行结果；API 编辑仍在独立 API 配置页完成。

截图中可见：顶部 API 路由状态卡和“前往 API 配置/手动运行一轮/重试最近失败楼层/刷新状态”操作；下方运行与触发设置、保存设置、当前聊天/世界书目标/状态说明和本次运行结果。

初步观察与建议：

- “API 路由状态”放在自动演变页顶部是合理的，但四个摘要项“当前来源、主模型、备用路由、API
  Key”需要保持与 API 配置页一致的中文状态口径。当前 `未配置`、`未配置可用来源`、`状态不可用`
  信息重复且下一步不够明确，建议合并成一条主状态和一条原因/下一步提示。
- “前往 API 配置”是当前最重要的引导，应在 API 未就绪时成为明显的主按钮；“手动运行一轮”和“重试最近失败楼层”在未配置或插件关闭时应清楚禁用原因，而不是仅呈现灰色按钮。
- “运行前先做连接测试（接入运行流程后生效）”属于可能影响真实 API 请求的设置，当前放在路由区/运行区附近容易与“模拟连接测试”混淆。建议明确标注这是运行前检查开关，并说明开启后仍可能产生真实请求，不能把它包装成安全模拟。
- 运行与触发设置中的字段过多且排列像普通表单：插件启用、自动触发、每轮 NPC、每轮其他对象、失败重试次数、重试间隔、楼层稳定轮询、连续稳定次数、当前角色卡主世界书、手动候选 NPC、自动同步世界书。建议分组为：
  - **运行开关**：插件启用、自动触发；
  - **处理规模**：每轮 NPC、每轮其他对象、手动候选；
  - **稳定与重试**：失败重试次数、重试间隔、楼层稳定轮询、连续稳定次数；
  - **世界书同步**：当前 primary 世界书、自动同步。
- 现在“插件启用”旁边的说明是“关闭时不监听、不运行、不修改世界书”，这是非常重要的安全语义，应保留并提高可见性；可考虑在顶部状态卡同时显示“插件已关闭 / 自动触发已关闭”，让用户不必滚动到设置区才知道当前状态。
- `每轮最多 NPC`、`每轮最多其他对象`
  等限制需要补充“这是每轮 AI 处理上限，不代表数据库总量”的短说明，避免用户误以为资料会被删除或只保留这些对象。
- “当前角色卡主世界书”目前显示完整、较长的名称；建议采用可折行的只读目标卡，并明确这是自动解析的 primary 世界书，不建议让用户在自动演变页直接编辑旧的手动书名字段。
- “手动候选 NPC”直接显示逗号分隔姓名，适合少量对象但可读性有限；可考虑标签化显示、去重和空状态说明，并明确它只影响手动运行候选，不会限制自动识别的数据库范围。
- “自动同步世界书”复选框应和“世界书投影”页的同步语义一致，旁边说明自动演变完成后何时同步、同步失败在哪里查看。
- “本次运行结果”在无记录时较空；应区分“尚未运行”“已跳过（未满足前置条件）”“运行失败”“运行成功但无变更”等状态，并给出下一步而非只显示“暂无运行记录”。
- 页面底部重复展示聊天、世界书目标和状态，建议保留一份就近状态摘要，避免顶部和底部各有一套相似但可能不同步的信息。
- 当前页面整体比 API 页更接近连续表单，但标签列、输入列和按钮区仍可以统一到工作台的表单栅格；窄窗口下应优先单列，并避免数值输入控件过宽造成阅读疲劳。

本轮截图补充确认：

- 页面顶部的 API 路由状态卡、运行设置卡和底部运行结果之间存在明显的层级断点。用户需要先读顶部“未配置/不可用”，再向下填写设置，最后在页面底部才看到聊天、世界书目标和运行状态；建议在页面顶部形成一条明确的“前置条件 → 运行设置 → 最近结果”阅读路径。
- API 未配置时，页面已经把“手动运行一轮”和“重试最近失败楼层”置为不可用，但禁用状态缺少就近原因。建议按钮下方或状态卡中直接显示“需要先配置可用 API 路由”，并让“前往 API 配置”成为唯一明确的下一步主操作。
- “当前来源 / 主模型 / 备用路由 / API
  Key”四张小卡在未配置时信息重复度较高；可以保留四项摘要，但增加一个统一的状态徽标和原因说明，避免用户逐项猜测“未配置”和“状态不可用”的区别。
- 运行设置表单的字段已经按若干行排列，但字段之间仍主要依赖左侧固定标签和大输入框来表达关系。建议实施时显式分成“运行开关、处理规模、稳定与重试、世界书同步”四个小组，每组带一句解释；这样能让“每轮最多 NPC”等限制与“重试间隔/稳定轮询”不被误读成同一种参数。
- 数值输入项缺少范围、单位和默认值语义的就地提示。例如 `200`、`1500`、`2`
  只有字段名，没有说明合理范围或对运行速度/额度的影响。可在不增加噪声的前提下补充单位和短帮助文本；具体默认值与运行逻辑保持不变。
- `插件启用`、`自动触发`、`自动同步世界书`仍呈现为原生复选框，尺寸、颜色和对齐与页面的暖色卡片风格不完全一致。后续可统一为带当前状态文字的开关控件；“关闭时不监听、不运行、不修改世界书”这条保护语义必须继续显眼。
- “当前角色卡主世界书”是只读目标信息，但现在看起来像普通可编辑输入框；建议改成只读目标卡或带复制/查看详情的摘要，明确它是自动解析出的当前角色卡
  `primary` 世界书。
- “手动候选 NPC”用逗号分隔姓名，在少量角色时可用，但随着候选增加会难以校对。建议改成可删除的姓名标签，并显示去重后的数量；仍保持它只影响手动运行、不改变数据库全量资料的语义。
- “保存设置”按钮位于表单卡片之外，视觉上与表单的从属关系不够强；建议放在设置卡底部的操作栏，并同时显示保存成功/失败反馈。顶部“刷新状态”则应保持为状态读取操作，不与保存混在一起。
- 页面底部的聊天名称、世界书目标和状态说明与顶部/设置区的信息有重复。后续可保留一份完整运行上下文摘要，另一处只显示简短状态，避免同一目标出现两套可能不同步的文字。
- “本次运行结果”在无记录时只显示“暂无运行记录”，空白区域较大。建议按状态区分“尚未运行”“因前置条件跳过”“运行失败”“成功但无变更”，并提供对应下一步；不应在没有运行记录时伪造统计。
- 该页整体纵向较长，第二张截图显示用户需要滚动才能看到保存反馈和运行结果。后续验收应检查 100%/110%/125% 缩放、嵌入式视口和滚动时顶部卡片/输入焦点是否被遮挡；不建议单纯压缩控件高度来解决长度问题。

- 是否允许在自动演变页直接编辑候选 NPC，还是仅显示摘要并将详细候选管理放到世界资料页？
- 手动运行按钮是否需要二次确认，至少在真实 API 路由可用时明确提示可能消耗额度？
- 插件启用、自动触发和自动同步是否应采用带状态说明的开关卡，而不是普通复选框？

### 4.8 填表提示词

**状态：已看图，待综合定稿。**

页面职责：维护世界演变使用的多消息提示词草稿，支持消息角色与顺序调整、启用/停用、导入导出和样例载入；当前页面明确只保存草稿，不直接参与真实 AI 调用。

截图中可见：顶部草稿状态说明与导入/导出/样例/保存工具栏，绿色提示说明，多张 SYSTEM/USER/ASSISTANT 消息卡片，消息启用开关、上移/下移、删除按钮，以及底部“添加消息”入口。

初步观察与建议：

- “提示词工作台”和侧栏“填表提示词”是两个称呼。建议确定一个面向用户的主名称，另一个作为副标题或导航说明，避免用户以为进入了两个不同功能。
- 顶部已经明确“仅保存草稿、不会参与真实 AI 调用”，这是很重要的安全边界，应保留为稳定状态徽标；同时建议把“草稿已载入”改成带颜色和时间/来源的状态提示，明确它是当前内存草稿、已保存草稿，还是刚载入的样例。
- `revision 0`
  出现在草稿页顶部容易被理解为提示词版本或数据库版本。需要确认它是否真的与该页草稿有关；若无直接关系，应改成“草稿版本”或降低/移除，避免把草稿保存和世界资料 revision 混为一谈。
- 导入 JSON、导出 JSON、载入清理版样例、保存草稿目前处在同一排，视觉权重接近，但作用和风险不同。建议分成“文件操作”“样例/清理”“保存当前草稿”三组，并明确载入样例是否会覆盖未保存内容；导入前应有格式校验和覆盖提示。
- “载入清理版样例”可能会改变原提示词内容。绿色说明条虽然提供了背景，但没有明确显示修改前后差异。建议提供预览/摘要，说明哪些段落被移除或改写；不要让用户误以为只是读取一个只读示例。
- 绿色提示条同时承担样例说明、内容清理说明和未接入运行链路说明，信息密度较高。建议拆成“当前状态”与“样例说明”两层，前者使用稳定状态徽标，后者在可折叠帮助中展示，避免把重要安全状态埋在长句中。
- 每张消息卡片的 `SYSTEM`、`USER`、`ASSISTANT`
  标签是技术角色名，可保留真实 payload 值，但界面上建议显示中文解释（系统、用户、助手）并保留英文值作为次级信息。角色值不能被视觉改名逻辑误改。
- 消息卡右侧的启用、上移、下移、删除控件结构清楚，但图标按钮缺少文字提示；应补充悬停提示、键盘可达性和明确的删除确认/撤销反馈。第一条上移、最后一条下移的禁用态要有可理解原因，而不只是变淡。
- `启用`
  的作用需要在就地帮助中说明：停用消息是暂时不参与导出/运行，还是只影响当前草稿展示。这个语义必须与未来真实运行链路保持一致；当前页面不能因为是草稿就让用户猜测。
- 多个文本区高度较大但仍会出现内部滚动，长提示词的编辑体验偏重。建议支持展开/全屏编辑、自动增高或明确的“编辑长文本”入口，同时保留卡片级排序和状态控制；不要简单把所有文本区无限拉高。
- 提示词里包含 `{{world_context}}`、`{{latest_message}}` 等模板变量，以及 `baseRevision`/`operations`
  等 JSON 片段。建议提供变量说明、格式检查和未识别变量警告，但不要在普通视图中强行改写内容；错误应在保存/导出前就地指出。
- 顶部提示中提到“多角色消息链”和数据库 `operations`
  格式，说明这页实际上同时面对提示词编辑和运行协议两个概念。建议增加轻量的“消息链预览/导出结构”摘要，让用户知道当前顺序、启用消息数和导出格式，而不必只靠逐个文本区判断。
- 当前空白区域较少，卡片堆叠逻辑比自动演变页清楚；但当消息很多时，顶部工具栏和底部“添加消息”会离得很远。建议提供固定/悬浮的消息链操作条，或在消息数量较多时增加目录/折叠，不改变消息顺序。
- 底部“添加消息”使用虚线大按钮，语义直观；建议新增消息时先选择角色并插入到指定位置，或提供默认角色与插入位置说明，避免每次只能追加后再反复上移。
- 页面需要明确区分“当前草稿已保存”“存在未保存修改”“导入失败”“导出完成”“样例已载入”。这些反馈不应只靠按钮颜色或一行小字表示，且不能与真实 API 调用成功/失败状态混用。
- 后续验收需检查：长文本滚动、消息顺序保持、禁用消息导出规则、导入异常 JSON、模板变量保留、刷新/关闭页面时未保存提醒，以及 100%/110%/125% 缩放和窄窗口下工具栏折行。

本页结论待与后续页面一起综合定稿。

### 4.9 备份与迁移

**状态：已看图，待综合定稿。**

页面职责：导出和导入当前聊天数据库，选择旧版备份进行迁移预检，以及在明确确认后清空当前聊天数据库。

截图中可见：顶部“数据库是事实源、世界书只是按需重建的投影”说明，当前聊天标识，数据库导出/导入卡片，A0.0.5 旧版迁移入口，以及单独的危险操作卡片。

初步观察与建议：

- 页面整体分区是正确方向：普通备份、旧版迁移、危险操作已经被分开，且危险区有红色标题和“请先导出备份”的提醒。后续应保留这种风险分层，不要把清空操作放回普通工具栏。
- 当前普通按钮都是相近的米色样式，`清空当前聊天数据库`虽然有红色小标题，但按钮本体仍接近普通操作。建议使用明确的危险按钮样式，并在二次确认中显示目标聊天、当前记录数、revision、operations 数量和可能受影响的
  `WorldEvolution-*` 投影条目。
- 导出和导入目前并列，但导入的行为边界不够明确。需要在按钮附近说明是覆盖、合并、追加还是生成新 revision；导入前应显示文件名、备份版本、记录数、生成时间、目标聊天和冲突处理方式，并提供预览/确认，而不是选文件后立即写入。
- “导出数据库 JSON”需要明确导出范围和隐私边界：是否包含世界资料、楼层运行、operations、检查点、提示词草稿、API 配置、API
  Key、世界书投影状态等。UI 不应让用户猜测导出的 JSON 是否包含敏感凭据；API Key 等敏感信息应明确排除或脱敏。
- 旧版迁移入口目前用一条很长的“选择 A0.0.5 备份并迁移”按钮表达所有步骤。建议拆成“选择文件 → 读取并校验 → 预览迁移报告 → 确认导入”四步状态；显示支持的来源版本、目标版本、无法自动迁移的字段和需要用户决策的冲突。
- 版本号不应写死为 `A0.0.5`。当前工作台侧栏已经显示
  `A0.1.0-alpha.13`，迁移入口应动态显示“支持的旧版格式”或由运行时代码提供版本，避免页面升级后出现过时文案。
- 顶部两条绿色说明都在讲安全/事实源，但语气和视觉权重接近。建议拆成一条常驻的“数据模型说明”和一条按当前操作变化的状态/警告，避免危险操作的关键提示被普通说明淹没。
- “已读取……数据库”当前以绿色成功色显示，但它更像当前上下文摘要，不一定代表刚刚完成了可恢复备份。建议改成中性的“当前目标”信息，并附记录数、revision、最后更新时间；真正的导出/导入成功再使用成功色和明确时间。
- 清空操作需要明确它只清空数据库，还是也会处理当前角色卡世界书中的 `WorldEvolution-*`
  投影。由于世界书是可重建投影，清空后若保留旧条目可能产生孤儿数据；若会清理，则需要在确认对话中明确列出影响范围。不能只写“当前聊天数据库”。

- 页面下半部留白较大。可以把“当前数据库摘要”和“最近一次备份/迁移结果”放入普通操作区旁边，帮助用户判断是否需要导出；不建议为了填满页面增加与备份无关的统计。
- 后续验收需覆盖：导出文件下载和内容范围、错误/损坏 JSON、版本不兼容、导入预览、重复导入、取消确认、清空前强制备份提示、清空后投影一致性、刷新后状态恢复，以及 100%/110%/125% 缩放和窄屏下危险区是否仍然醒目。

## 7. 分阶段实施计划

本轮不采用“一次性重做全部页面”的方式。计划书可以一次写完整，但代码实施必须严格按阶段推进：每个阶段只处理一个明确范围，完成后进行本地页面检查和功能回归，确认没有破坏后再进入下一阶段。

### U0：基线、隔离与公共样式准备

目标：建立统一 UI 所需的样式基线，不改变任何数据库、API、世界书、提示词或自动演变业务逻辑。

范围：

- 盘点现有页面共用组件、CSS 变量、卡片、按钮、表单、表格、状态提示和空状态；
- 统一颜色、文字对比度、字体层级、圆角、边框、阴影、间距和内容最大宽度；
- 统一左侧导航、顶部面包屑、页面标题、revision/版本显示和关闭按钮；
- 统一成功、警告、危险、禁用、未配置、加载和空状态语义；
- 为窄窗口、嵌入式视口和 100%/110%/125% 缩放建立验收基准。

完成标准：公共样式可被各页面复用；版本号使用统一来源；未改变任何业务状态和数据结构；能够截取一张基线页面作为后续对照。

回退点：只回退公共样式文件和版本显示改动，不触碰业务模块。

### U1：共用工作台外壳

目标：先稳定所有页面共同依赖的外壳，避免逐页修改时重复修复导航和页头。

范围：

- 侧栏品牌、聊天标识、导航分组、当前选中态和底部状态；
- 页面内容区的宽度、滚动容器、顶部固定区域和卡片对齐；
- revision、数据库版本、插件版本和运行状态的显示层级；
- 聊天名称截断、悬停查看、窄屏折叠和关闭行为。

验收：在所有现有路由间切换，导航选中态、标题、滚动位置和关闭按钮不异常；不改变路由和页面功能。

### U2：总览页

目标：让用户进入工作台后立即知道当前聊天是否具备运行条件，以及下一步该去哪里。

范围：

- 统计卡统一网格、宽度、标题和数字层级；
- 增加 API、自动演变和世界书投影的准备状态摘要，但不重复 API 编辑表单；
- 优化最近楼层空状态、常用入口和主操作；
- 收敛“数据库事实源/世界书投影”说明，避免大段技术文本占据首屏。

验收：无数据、部分配置、已配置和存在失败记录四种状态都能读懂；入口跳转正确；不新增真实 API 调用。

### U3：API 配置页

目标：把预设、路由、Key 脱敏和工作流助手兼容状态整理成清晰的配置流程。

范围：

- 预设列表/编辑表单采用稳定的左右结构或紧凑栅格；
- 按“基本信息、连接信息、请求策略、路由资格”分组字段；
- 将主路由、备用路由、来源开关和有效路由结果放在同一阅读路径；
- 兼容桥接改成明确的状态卡；
- 统一模拟测试、保存预设、保存路由和失败提示；
- 修复版本标识、滚动遮挡、输入焦点被顶栏覆盖等视觉问题，但不改变路由优先级和真实调用逻辑。

验收：可创建、编辑、删除和模拟测试预设；Key 始终脱敏；主备路由状态准确；API 未配置时不会误启用真实运行。

### U4：世界资料页

目标：降低资料管理的技术门槛，同时保留 JSON 高级编辑能力。

范围：

- 统一分类导航、统计卡和当前聊天数据库摘要；
- 设计新增记录的普通字段入口与 JSON 高级入口的关系；
- 明确“提供给 AI”等可见性选项的含义；
- 优化搜索、空表、校验错误、保存成功和写入 NPC 的反馈；
- 技术字段保留在详情/高级视图，主表优先显示用户可理解的信息。

验收：七类资料切换、搜索、新增、编辑和校验行为不变；错误不会丢失已输入内容；JSON 与普通表单的结果一致。

### U5：楼层记录页

目标：让楼层运行、revision 操作和检查点的关系更容易理解。

范围：

- 重做与楼层职责相关的统计摘要；
- 区分普通刷新、创建检查点和确定性重建；
- 将 `revision`、`operations`、`stale` 等技术字段降为辅助信息；
- 为三张空表提供不同的引导文案；
- 以展开区承载 operations 变更类型、对象分类、对象 ID 和名称；
- 状态标签使用中文与语义色区分；楼层运行记录保留实际结果 revision，包括已过期结果。

验收：明确重建不会重新调用 AI；仅允许选择确有版本操作的楼层；说明目标楼层操作被跳过、受影响历史版本标为过期并保留，以及聊天消息/世界书/检查点不被自动改动。刷新、创建检查点和确定性重建入口保持独立。

### U6：世界书投影页

目标：清楚表达数据库到当前角色卡 `primary` 世界书的同步关系和影响范围。

范围：

- 拆分待处理、失败、缺失、漂移和孤儿等状态的展示；
- 将只读重新检查、同步并修复差异、完整重建做成有风险层级的操作组；避免把同一 reconcile 行为展示成两个不同按钮；
- 主表优先显示投影类型、对象、账本状态和来源版本；UID、稳定键、指纹和错误等进入详情；
- 分清 IndexedDB 同步账本状态与对 primary 世界书的实时检查状态；
- 明确操作基于世界演变托管元数据而不只是 `WorldEvolution-*` 名称；说明未标记条目不会处理，并对旧版缺少 `chatKey`
  的托管条目给出归属不确定警告；
- 优化长世界书名称、单条投影和空状态布局。

验收：模拟同步、缺失、漂移、孤儿和完整重建状态；明确状态来源与操作范围；页面改动不得触发真实同步或重建。

### U7：自动演变页

目标：把“前置条件、运行设置、最近结果”组织成连续流程。

范围：

- 顶部 API 状态卡改成主状态、原因和下一步操作；
- 按运行开关、处理规模、稳定与重试、世界书同步分组；
- 统一开关控件、数值单位、范围提示和只读世界书目标；
- 手动候选 NPC 改为可校对的标签/摘要；
- 将保存设置放回表单操作栏；
- 区分尚未运行、跳过、失败、成功无变更和成功有变更；
- 明确真实 API 可能产生额度消耗，保持模拟测试与真实运行边界。

验收：插件关闭、API 未配置、自动触发关闭、运行成功、运行失败和无变更状态均能正确呈现；手动运行和重试按钮禁用原因准确。

### U8：填表提示词页

目标：让多消息提示词编辑安全、可读，并明确“草稿不参与真实运行”。

范围：

- 统一草稿状态、未保存修改、样例载入、导入和导出反馈；
- 将文件操作、样例/清理、保存草稿分组；
- 优化 SYSTEM/USER/ASSISTANT 消息卡片、启用、排序、删除和添加消息；
- 提供模板变量说明、未识别变量警告和 JSON 格式校验；
- 支持长文本展开/全屏编辑或合理自动增高；
- 明确导入、样例载入是否覆盖未保存内容，并增加预览/确认。

验收：消息顺序、启用状态、模板变量、导入导出内容保持一致；刷新/关闭时未保存提醒准确；页面不会接入真实 AI 调用。

### U9：备份与迁移页

目标：将备份、旧版迁移和清空操作做成风险清晰的恢复流程。

范围：

- 导出显示数据范围和敏感字段排除规则；
- 导入先做文件校验、版本识别、记录统计和冲突预览，再确认写入；
- 旧版迁移拆成选择、读取校验、预览报告、确认导入；
- 动态显示支持的旧版格式，移除写死的过时版本号；
- 清空操作使用危险样式、二次确认和影响范围摘要；
- 明确清空数据库是否同步处理 `WorldEvolution-*` 世界书投影，并提供备份恢复入口。

验收：损坏文件、不兼容版本、重复导入、取消确认、清空后恢复和投影一致性均可验证；不会误删其他聊天或用户世界书条目。

#### 2026-10-01 基线验收结果（alpha.14）

- **安全边界**：在本地已打开的 alpha.14 页面检查；未提交表单、未导入/导出/迁移/清空数据库、未运行或重试演变，未调用真实 API，也未同步、修复或重建角色卡世界书。临时查看 110% 与 125% 后已恢复原来的 100%，浏览器中最终比例与验收前一致；主题保持奶油风。

- **核心自动化回归**：世界演变及数据库相关测试 **88/88 通过**；相关 ESLint、生产构建与 `git diff --check` 通过。全仓测试 **431 通过、6 个测试文件失败**，因此全仓结果不是全绿。失败文件为工作流助手 `bridge/post-process-api.test.ts`、`tasks/nested-tag-relay-sync.test.ts`、`tasks/plot-worldbook-scan.test.ts`、`tasks/prompt-auto-segment-ops.test.ts`、`tasks/task-extract-tags-merge.test.ts`，以及 `资产账本/parse.test.ts`。只读审查显示这些失败涉及测试加载器无法导入 HTML、标签格式断言与实际换行不一致、自动导入的 lodash `_` 在裸 tsx 测试中缺失、大小写归一化断言不一致，以及 ESM-only 依赖在当前测试上下文中的导入限制；这些源文件均不在 U0–U9 本次 UI 改动范围内，未在本轮扩修。

- **验收结论**：U10 的 alpha.14 基线检查收口，alpha.14 仍可用于后续只读页面验收；但记录了上述窄屏/缩放视觉缺陷和 6 个全仓测试例外。该结论不是“UI 无缺陷”或“全仓全绿”，也不批准推送 `main` 或发布新版。视觉缺陷留给 U11；若未来要让全仓测试全绿，应另行修复并单独回归那 6 项。

#### 设计原则

- 保留现有奶油色主背景与鼠尾草绿品牌强调色，不把整个页面刷成绿色；卡片、提示、导航和状态使用有层次的浅色面。
- 以语义 token 管理背景、卡片、边框、主/次文字、链接、焦点环、成功、提示、警告、危险和禁用状态；避免组件自行散落黑色、深蓝色或低对比度浅灰值。
- 普通文字使用柔和但足够深的灰绿/暖灰，不用纯黑作为大面积文字色；标题、正文、说明文字需有清楚层级，说明文字仍须清晰可读。
- 信息与成功提示使用淡灰绿/淡鼠尾草绿；一般提醒使用淡琥珀/米黄色；危险操作容器使用用户提供参考图方向的浅粉/浅玫瑰色，危险标题、边框和执行按钮采用更深的玫瑰红。粉色只表示危险，不覆盖普通警告。
- 深色主题继续保持深色方案，但按同一套语义对应设计，不把浅色主题的粉绿底直接套到深色主题；地雷色主题保持其独立定位，只修正对比度和组件一致性。
- 颜色不能成为唯一状态线索；状态文字/图标继续保留，键盘焦点、禁用态和鼠标悬停态也需清楚。
- 色值先作为语义角色讨论，具体 HEX 在实施前以实际页面截图和对比度检查确定；不得为了“柔和”而把文字淡化到难以辨认。
